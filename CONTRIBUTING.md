# 🧭 Руководство для разработчиков

## 🚀 Общие принципы разработки

- Вся работа ведётся через **ветки** — никаких прямых коммитов в `main` или `develop`.
- Каждый разработчик работает в **своей ветке**, созданной от актуальной `develop`.
- После завершения задачи — оформляется **Pull Request** (PR) с понятным описанием и ссылкой на задачу (например, в Jira, Trello, ClickUp и т.д.).
- Код должен соответствовать стандартам форматирования (используйте `prettier`, `eslint`, `black`, `flake8` и т.д.).
- Обязательно писать **понятные коммиты** и **тесты** для критичных участков кода.

---

## 🌿 Ветки

### Основные ветки

| Ветка       | Назначение |
|--------------|-------------|
| `main`       | Содержит стабильные, протестированные релизы |
| `develop`    | Основная ветка для активной разработки |

### Ветки задач

Создавайте ветки по шаблону:

```
<тип>/<номер-задачи>-<краткое-описание>
```

#### Примеры:
```
feature/123-add-login-page
bugfix/234-fix-user-auth
hotfix/312-fix-production-error
refactor/145-cleanup-api-structure
docs/210-update-readme
```

#### Типы веток:
- `feature` — новая функциональность  
- `bugfix` — исправление бага  
- `hotfix` — срочное исправление на продакшене  
- `refactor` — улучшение структуры кода без изменения логики  
- `docs` — обновление документации  
- `test` — добавление или правка тестов

## 📝 Коммиты

### Формат коммитов (Conventional Commits)

```
<тип>(область): <краткое описание>
```

#### Примеры:
```
feat(auth): add login form and JWT handling
fix(ui): correct button alignment on mobile
refactor(api): split user controller into smaller modules
docs(readme): add branching strategy section
test(core): add unit tests for utils
```

#### Возможные типы:
- `feat` — новая фича  
- `fix` — исправление ошибки  
- `refactor` — рефакторинг кода  
- `chore` — технические задачи, не влияющие на код  
- `docs` — изменения в документации  
- `test` — добавление/изменение тестов  
- `style` — исправление форматирования (пробелы, отступы и т.д.)  
- `perf` — улучшение производительности  

#### Правила:
- Сообщение должно быть **на английском** (желательно), **в настоящем времени**.
- Описание должно быть **лаконичным и понятным**.
- Если коммит связан с задачей — добавляйте номер:
  ```
  feat(api): implement user registration (#123)
  ```

---

## 🧩 Pull Request (PR)

- Название PR = краткое описание задачи:
  ```
  Add user registration API (#123)
  ```
- В описании PR указывайте:
  - Что сделано
  - Как протестировать
  - Ссылку на задачу / тикет
- Один PR = одна логическая задача.  
  Не смешивайте рефакторинг, фиксы и новые фичи в одном PR.

## 🔧 Настройки Git Hooks (рекомендуется)

Добавьте в проект pre-commit hooks для автоматической проверки:
- Форматирования (`prettier`, `black`)
- Линтинга (`eslint`, `flake8`)
- Проверки коммит-сообщений (например, через `commitlint`)

## 🧱 Пример рабочего цикла

```bash
# 1. Получаем последнюю develop
git checkout develop
git pull origin develop

# 2. Создаём ветку
git checkout -b feature/123-add-login-page

# 3. Работаем над задачей
git add .
git commit -m "feat(auth): add login form"

# 4. Отправляем изменения
git push origin feature/123-add-login-page

# 5. Оформляем Pull Request в develop
```

## ✅ Финализация

После ревью и успешных тестов:
- Ветка мержится в `develop`
- Для релиза формируется `release/x.x.x` и мержится в `main`
