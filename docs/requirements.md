# 📘 Technical Requirements — Smart Gift Assistant

## 1. Введение

Smart Gift Assistant — интеллектуальная система, которая помогает пользователю подбирать подарки и управлять важными событиями.  
Пользователь взаимодействует с системой через чаты, формирует запросы, получает рекомендации подарков и создаёт напоминания о важных датах.  
Цель проекта — упростить подбор подарков и автоматизировать планирование важных событий.

---

## 2. Use-cases

Use Cases подробно описаны в документе ЛР-1 и включают:

- UC1 — Регистрация
- UC2 — Вход в систему
- UC3 — Просмотр истории
- UC4 — Управление профилем
- UC5 — Запрос рекомендаций подарков
- UC6 — Уточнение/фильтрация параметров
- UC7 — Работа с чатами
- UC8 — Работа с напоминаниями
- UC9 — Дополнительные вопросы/персонализация

---

# 3. Функциональные требования (FR)

Ниже — полный перечень требований по каждому Use-case.

---

## UC1 — Регистрация

- ✅**FR-1.** Система должна предоставлять пользователю возможность создать учётную запись.
- ✅**FR-2.** Система должна проверять корректность введённых регистрационных данных.
- ✅**FR-3.** Система должна сохранять новый аккаунт в базе данных (PostgreSQL).
- ✅**FR-4.** Система должна автоматически авторизовывать пользователя после успешной регистрации.
- ✅**FR-5.** Система должна информировать пользователя об ошибках при некорректных данных.

---

## UC2 — Вход в систему

- ✅**FR-6.** Система должна предоставлять форму для ввода учётных данных.
- ✅**FR-7.** Система должна проверять корректность email и пароля.
- ✅**FR-8.** Система должна выдавать JWT-токен при успешной авторизации.
- ✅**FR-9.** Система должна информировать пользователя об ошибке при неверных данных.

---

## UC3 — Просмотр истории действий

- ✅**FR-10.** Система должна хранить историю пользовательских запросов.
- ✅**FR-11.** Система должна предоставлять пользователю список предыдущих запросов и полученных рекомендаций.
- ✅**FR-12.** Система должна уведомлять пользователя, если история отсутствует.

---

## UC4 — Управление профилем

- ✅**FR-13.** Система должна позволять редактировать данные профиля (имя, фамилия, пол, описание, дата рождения, ссылка на Telegram).
- ✅**FR-14.** Система должна сохранять изменения в базе данных.
- ✅**FR-15.** Система должна учитывать обновлённые данные при формировании рекомендаций.
- ✅**FR-16.** Система должна возвращать пользователю сообщение об ошибке при некорректных данных.

---

## UC5 — Запрос рекомендаций подарков

- ✅**FR-17.** Система должна предоставлять возможность ввода текстового запроса.
- ✅**FR-18.** Система должна использовать LLM для создания рекомендаций.
- ✅**FR-19.** Система должна сохранять полученные рекомендации в истории запросов.
- ✅**FR-20.** Система должна возвращать результат в текстовом виде (список подарков, ссылки, пояснения).
- ❌**FR-21.** Система должна уведомлять пользователя, если ответ не может быть сгенерирован.

---

## UC6 — Уточнение/исключение параметров

- ✅**FR-22.** Система должна позволять пользователю уточнять запрос (пол, возраст, бюджет, отношение к получателю).
- ✅**FR-23.** Система должна пересчитывать рекомендации на основе уточнённых данных.
- ✅**FR-24.** Система должна предоставлять обновлённый список рекомендаций.

---

## UC7 — Работа с чатами

- ✅**FR-25.** Система должна позволять создавать новые чаты.
- ✅**FR-26.** Система должна предоставлять доступ к списку чатов.
- ✅**FR-27.** Система должна позволять просматривать историю сообщений чата.
- ✅**FR-28.** Система должна позволять переименовывать чат.
- ✅**FR-29.** Система должна позволять удалять чат вместе с сообщениями.

---

## UC8 — Работа с напоминаниями

- ✅**FR-30.** Система должна позволять создавать новые напоминания.
- ✅**FR-31.** Система должна позволять редактировать существующие напоминания.
- ❌**FR-32.** Система должна удалять напоминания по запросу пользователя.
- ✅**FR-33.** Система должна отправлять уведомления пользователю (email или Telegram).
- ✅**FR-34.** Система должна проверять корректность даты и времени.
- ✅**FR-35.** Система должна сохранять напоминания в базе данных.

---

## UC9 — Дополнительные рекомендации / уточняющие вопросы

- ✅**FR-36.** Система должна генерировать уточняющие вопросы для повышения качества рекомендации.
- ✅**FR-37.** Система должна учитывать ответы пользователя при дальнейших рекомендациях.
- ✅**FR-38.** Система должна передавать уточняющую информацию в LLM.

# 4. Нефункциональные требования (NFR)

## 4.1 Производительность

- Система должна обеспечивать **время отклика API ≤ 1 сек**.
- Время генерации ответа LLM должно быть **≤ 25 сек**.
- Время обработки напоминания при создании — **≤ 2 сек**.

---

## 4.2 Пропускная способность

- Система должна поддерживать **от 100 одновременных пользователей**.
- Должно поддерживаться **до 200 запросов в минуту**.

---

## 4.3 Доступность

- Uptime системы должен быть **≥ 99%**.
- Время восстановления после сбоя — **≤ 30 минут**.

---

## 4.4 Надёжность

- При сбое внешнего LLM-сервиса возвращается безопасное сообщение.
- История и напоминания должны сохраняться корректно.

---

## 4.5 Использование ресурсов

- Система должна работать на Windows, macOS, Linux и мобильных браузерах.
- Должна поддерживаться работа при низкой скорости Интернета.

---

## 4.6 Безопасность

- JWT-токены используются для авторизации.
- Пароли должны храниться в хэшированном виде (bcrypt).
- Передача данных — только через HTTPS.

---

## 4.7 Масштабируемость

- Возможность контейнеризации (Docker).
- Возможность вынести LLM, Redis, PostgreSQL в отдельные сервисы.

---

## 4.8 Удобство использования

- Интерфейс должен быть простым и интуитивным.
- Поддержка русского языка.
- Время обучения пользователя ≤ 5 минут.

---

## 4.9 Поддерживаемость

- Система должна иметь OpenAPI-документацию.
- Минимум 30% автотестов (юнит/интеграционных).

---

## 4.10 Переносимость

- Система должна корректно работать в Docker.
- Поддержка современных браузеров.

---

# 5. Технологический стек

- **Frontend:** Vue.js, TypeScript, Pinia, Tailwind
- **Backend:** Node.js (Express + TypeScript)
- **База данных:** PostgreSQL
- **Кэш/очереди:** Redis
- **AI Layer:** LLM API
- **Векторное хранилище:** Chroma

---

# 6. Архитектурные принципы

- Клиент-серверная архитектура с REST API.
- Разделение ответственности (SRP).
- Модульность, расширяемость, единый стиль API.
- Использование JWT и bcrypt для безопасности.
- Docker для воспроизводимой инфраструктуры.
- Fail-safe: при ошибке внешнего сервиса — мягкое сообщение пользователю.

---

# 7. Ограничения и допущения

- LLM API является внешним сервисом и не контролируется полностью.
- Фото-анализ отсутствует — рекомендации генерируются текстово.
- Поддерживаются только современные браузеры.
- Качество рекомендаций зависит от выбранной модели LLM.
